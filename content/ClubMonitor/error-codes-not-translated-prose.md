Club Monitor had no localization at all: every handler message, every email template and every XAML string was hardcoded English. Making the whole application multilingual — English, French and Spanish — touches nearly every handler and every page, so it went in as a phased plan rather than one enormous change. This is the backend half: the decisions, the error-code contract, and the notification templates.

## The decision that shapes everything else

The first question is deceptively simple: when the API refuses a request, what language is the refusal in?

The tempting answer is to translate the message — read `Accept-Language`, pick a resource, return French prose. It is also the wrong one. It makes every failure message part of the wire contract, so improving the English wording silently breaks clients matching on it. It forces the server to own translations for text it never renders. And it fails outright the moment the recipient of a message is not the caller.

So the API does not translate. `HandlerResult<T>` keeps its existing `HandlerError` enum, which decides the HTTP status, and gains a second one: `ErrorCode`, with one member per distinct failure. The response body becomes:

```json
{ "error": "ClubNotFound", "message": "Club not found." }
```

`error` is the stable contract clients code against. `message` is an English-only diagnostic fallback that no client should ever display verbatim. Each client owns its own translations and maps codes to its own localized strings.

The second decision follows from the same reasoning. Some content genuinely is generated by the server — a two-factor code by email or SMS, an invitation notification later. That text has to be in *some* language, and `Accept-Language` on the triggering request is no help, because the recipient frequently is not the caller: an Admin inviting a member is one person acting and another person reading. So the user record gained a nullable BCP-47 `PreferredLanguage` (`null` meaning `en`), exposed on `GET /api/auth/me` and settable via `PUT /api/auth/language`.

## Growing the enum without stopping the world

The first implementation phase added infrastructure only: the `ErrorCode` enum with a small starter set, a `Code` property on `HandlerResult<T>`, the new response shape, a `SupportedCultures` constant, the `PreferredLanguage` column and its migration, and the handler and endpoint to set it.

The trick that kept this reviewable was making the new argument optional — `ErrorCode code = ErrorCode.Unspecified` — so every existing call site in the codebase kept compiling untouched. The sweep could then proceed one feature area at a time.

Auth went first, being the most user-visible: 22 new codes across 52 call sites in twelve handlers. The remaining areas — Clubs, Competitions, Matches, Memberships and Sports — added another 27.

Two judgement calls recur throughout:

- **Identity's own errors collapse to one code.** Failures composed from `IdentityResult.Errors` (account creation, setting a password, enabling two-factor) all map to `IdentityOperationFailed`. The message is already Identity's own composed English string and does not split meaningfully into finer-grained codes.
- **The same concept reuses the same code.** `NotClubAdmin` covers every club-Admin guard; `MembershipNotFound` covers an absent invite, join request or member; `PhoneNumberRequired` covers both enabling SMS two-factor without a number and sending a code to an account with none on file.

Then the part that made the sweep provable. With every call site converted, the default came off: `NotFound`, `Forbidden`, `Invalid` and `Conflict` now *require* a code. The API building clean with the parameter mandatory is the proof that nothing was missed — and from here a new failure path cannot compile without naming its code. `Unspecified` survives only as the enum's zero value carried by successful results.

## A test fixture that had been lying

Adding failure-path coverage for the sweep turned up a bug in the tests rather than in the code. `SeedData` set only `Email` on its seeded users, but Identity writes `NormalizedEmail`, `UserName`, `NormalizedUserName` and `SecurityStamp` as well. `InviteMemberHandler` looks users up by `NormalizedEmail`, so it silently missed every seeded user and treated a duplicate invite as brand new. The new `Inviting_an_existing_member_conflicts` test failed until the seed matched what Identity actually writes. The handler was correct all along; the fixture was not.

## Localizing what the server does send

With `PreferredLanguage` in place, the two-factor email and SMS became the first genuinely translated server output: `NotificationStrings.resx` plus `.fr` and `.es` siblings, with keys for the email subject, the email body and the SMS body. Each entry carries a translator comment noting that "Club Monitor" is a product name, what `{0}` is, and that the SMS string must stay inside a single 160-character segment.

The interesting constraint is what *not* to use. `IStringLocalizer` is the obvious tool and the wrong one: it always resolves against the ambient `CultureInfo.CurrentUICulture`, which on an API request is the caller's culture — exactly the wrong source when the recipient is someone else. `NotificationTemplates` takes the culture as an argument instead and calls `ResourceManager.GetString(key, culture)`, the official overload that accepts one directly. That also avoids mutating ambient culture on a shared request thread.

Stale preferences fall back rather than throw. If a language is dropped from `SupportedCultures` after users have selected it, those accounts must still be able to receive a sign-in code.

## Testing translations that fail silently

Thirteen tests cover the notifications, and two of them exist purely because of how quietly this can break.

`ResourceManager` falls back to the neutral resource when a key is missing from a satellite assembly. An untranslated string therefore looks perfectly healthy at runtime — it just shows English. So one test asserts that every non-default culture's rendering actually *differs* from English.

The other extracts the code from the **French** email and verifies it through `VerifyTwoFactorCodeHandler`. A translation that lost its `{0}` placeholder would render beautifully and lock the user out.

The API suite went from 61 to 103 passing tests across these phases. And `bin/Debug/net10.0/fr/ClubMonitor.Api.resources.dll` appears with no `.csproj` change at all — the SDK picks the `.resx` files up on its own.
